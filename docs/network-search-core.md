# Математическое ядро поиска улучшений дорожной сети

> Предлагаемая архитектура: проверенный дорожный граф и распределённый спрос → допустимые проекты → поиск отдельных улучшений и пакетов → полный расчёт эффекта. Небольшая обучаемая модель ускоряет выбор кандидатов для расчёта. Итоговые рекомендации подтверждает численный решатель.

**Статус:** проект решения, подготовленный по результатам исследования. Документ не подтверждает внедрение перечисленных механизмов или их производительность на наших данных.

**Читайте, если:** проектируете расчёт потоков, поиск инфраструктурных улучшений или проверяете обоснованность рекомендаций. **Связано:** [README проекта](README.md).

## 1. Какой результат должно выдавать ядро

Пользователь выбирает город, пару территорий, регион или всю РФ, задаёт цель и ограничения. Ядро возвращает проверенные варианты: где изменить существующую дорогу или добавить участок, какой локальный эффект это даст, как изменится индекс региона и какие ресурсы потребуются.

Для запроса «где улучшить связанность Невинномысска» результатом служит конкретный проект или пакет с геометрией дорог, показателями до/после и объяснением: какие направления получили более короткий путь, какие перегруженные участки разгрузились, где сохранились ограничения.

Поиск критических закрытий использует те же граф, спрос и расчёт доступности. Поломка привязки одного узла к сети не должна превращаться в вывод об изоляции города.

| Требование | Что считается выполнением |
| --- | --- |
| Воспроизводимость | Один снимок сети, спроса, параметров и seed даёт сопоставимый результат |
| Проверяемый эффект | Сохранены исходный расчёт, изменённая сеть, сходимость и метрики |
| Географическая осмысленность | Выделенная линия совпадает с оцениваемым участком; препятствия проверены |
| Честное сравнение | Все варианты используют одинаковый спрос, границы и определения метрик |
| Ограниченный поиск | Есть бюджет времени и полных расчётов, сохранён лучший проверенный результат |
| Разные масштабы | Всероссийский отбор и локальный расчёт связаны общими идентификаторами и версиями |

## 2. Где возникают опасные ошибки

Короткий жилой переулок может оказаться единственным ребром к узлу, представляющему весь город. Тогда корректный поиск пути по неверному представлению территории выдаст ложную транспортную катастрофу. Замена алгоритма кратчайшего пути такую ошибку не исправляет.

| Сбой | Требуемая защита |
| --- | --- |
| Весь город представлен одной точкой | Несколько транспортных зон и проверенных выходов к сети |
| После закрытия спрос переносится к удобному узлу | Одинаковые зоны и привязки до/после; закрытие может действительно разорвать доступ |
| Локальная рамка обрезает объезд и транзит | Внешние шлюзы, фоновый поток и проверка чувствительности к границе |
| Новая дорога проходит через жилой дом | Проверка коридора по препятствиям до оценки строительного предложения |
| Среднее время падает из-за исчезновения дальних поездок | Неизменная матрица спроса; недоступные поездки учитываются отдельно |
| Почти нулевой эффект выглядит как точная рекомендация | Проверка устойчивости знака и порядка вариантов при уточнении расчёта |
| Первый рассмотренный тип проекта становится победителем | Общий пул кандидатов; лимит выдачи отделён от бюджета поиска |
| Эффект пакета равен сумме одиночных эффектов | Пакет рассчитывается совместно с перераспределением потоков |

## 3. Территории должны иметь распределённый доступ к сети

### 3.1. Спрос задаётся транспортными зонами

Предлагается делить территорию на зоны по жилой застройке и населению, объединяя малые ячейки до управляемого размера. Размер выбирается по устойчивости результатов: укрупнение не должно менять ключевые выводы о связанности и приоритетных проектах.

Для каждой зоны хранятся вес населения, источники и привлекательность поездок, геометрия, допустимые подключения и распределение спроса между ними. При отсутствии наблюдаемой матрицы поездок применяется явно версионируемое правило её построения. Поиск показывает результат для выбранного сценария спроса; происхождение данных сохраняется в расчётном паспорте.

Суммарный спрос сохраняется:

\[
q_{ij}\geq 0,\qquad \sum_j q_{ij}=O_i,\qquad \sum_i q_{ij}=D_j.
\]

Оба ограничения применяются при согласованных суммах отправлений и прибытий. Если есть только отправления, используется соответствующая односторонне ограниченная постановка; отсутствующие назначения нельзя выдавать за измеренные.

### 3.2. Подключения зон не создают скрытых дорог

Каждая зона получает несколько подключений там, где к сети действительно есть доступ. Расстояния до ближайшего ребра недостаточно: учитываются реки, железные дороги, ограждения, въезды, направление движения и доступность для выбранного транспорта.

Подключение имеет стоимость доступа и вес. Через виртуальный центр зоны запрещается транзит между её выходами: иначе несколько подключений создадут бесплатный объезд внутри зоны. У AequilibraE есть механизмы создания коннекторов и блокировки транзита через центроиды; их применимость проверяется на нашем графе. [Создание коннекторов](https://www.aequilibrae.com/docs/python/v1.5.2/useful_links/_autosummary/aequilibrae.project.network.connector_creation.html), [API графа](https://aequilibrae.com/docs/python/V.1.1.4/useful_links/_generated/aequilibrae.paths.Graph.html).

При закрытии дороги используются исходные подключения. Нельзя автоматически перепривязать отрезанную зону за препятствие и тем самым восстановить несуществующий доступ. Если зона действительно имеет единственный мост, его закрытие должно сохранять эффект изоляции.

### 3.3. Дорожный граф согласован с правилами движения

Для направленного ребра нужны геометрия, длина, разрешённое направление, класс дороги, свободная скорость, пропускная способность по направлению и ограничения доступа. Запреты поворотов учитываются в маршрутизации, например через расширенный граф состояний.

Полосы относятся к направлению движения. Расширение не должно случайно удваивать общую пропускную способность обеих сторон. Самостоятельное увеличение скорости запрещено. Допустимы дополнительные полосы после географической проверки; ускорение поездок возникает из изменений сети и перераспределения потоков. Скорость новой дороги выводится из её проектных параметров.

Параллельные проезжие части объединяются в один проект для объяснения и визуализации, но сохраняют самостоятельные рёбра в расчёте. Геометрия проекта содержит точный набор изменяемых направлений.

Переход от ненаправленного графа к направленному требует новой версии исходного индекса. Значения из разных версий не сравниваются как эффект одного проекта.

## 4. Расчёт должен учитывать перераспределение потоков

### 4.1. Основной оценщик — статическое пользовательское равновесие

Для интерактивного поиска предлагается начать со статического распределения автомобильного спроса по сети. Водители выбирают маршруты с учётом времени движения; добавление мощности может изменить маршруты на других дорогах.

Для разделимых возрастающих функций времени используется постановка Бекмана:

\[
\min_x \sum_{a\in E}\int_0^{x_a}t_a(u)\,du,
\]

при сохранении потоков и выполнении доступного OD-спроса. Для недоступных пар отдельно фиксируется необслуженный спрос. Нельзя молча удалить его из исходной задачи.

Начальная функция задержки может иметь вид BPR:

\[
t_a(x_a)=t_a^0\left[1+\alpha_a(x_a/c_a)^{\beta_a}\right].
\]

Параметры и мощности задаются по классам дорог, имеют версию и проверяются на чувствительность. Такая постановка не воспроизводит распространение очередей между перекрёстками; если это существенно для выбранного проекта, нужна отдельная детализация узла или динамический расчёт.

Для прототипа решателя сравниваются текущий доступный алгоритм, Frank–Wolfe и Biconjugate Frank–Wolfe. Документация AequilibraE рекомендует BFW для практического распределения и описывает относительный разрыв сходимости. Это основание для нашего бенчмарка, без обещания конкретного ускорения. [Traffic Assignment Insights](https://www.aequilibrae.com/latest/python/traffic_assignment/traffic_assignment_insights.html).

### 4.2. Малые эффекты требуют более строгой проверки

Для каждого запуска сохраняются относительный разрыв, число итераций, остановка по лимиту, остатки баланса потоков и недоступный спрос. Разрыв вычисляется на согласованных стоимостях; смена стоимостей посреди проверки делает критерий некорректным.

Сходимость целевой функции сама по себе не гарантирует точность любой локальной метрики. Если кандидаты отличаются мало, лучшие варианты пересчитываются с более строгим допуском. Пока знак эффекта или порядок меняется при уточнении, вариант не получает подтверждённого преимущества.

Общий OD-спрос, параметры и способ инициализации фиксируются для сравнения. При случайной генерации сценариев используются одинаковые seed. Для повторных расчётов допускаются тёплый старт и кэш; эквивалентность результату холодного запуска проверяется на контрольной выборке.

### 4.3. Граница территории сохраняет внешний контекст

Локальный расчёт включает внутренние поездки, въезды и выезды, а также транзит через территорию. Внешние узлы представлены шлюзами с согласованными временами и объёмами. Простое обрезание графа по прямоугольнику не является завершённой моделью региона.

Для проектов рядом с границей область расширяется до стабилизации результата. Критерий стабилизации задаётся до эксперимента и сохраняется в его паспорте.

## 5. Локальный эффект и индекс региона отвечают на разные вопросы

Региональный индекс сохраняет общие рынки, веса и нормировку атласа. Локальный проект может давать полезный эффект в городе при почти неизменном среднем по большому региону.

| Показатель | Назначение | Правило сравнения |
| --- | --- | --- |
| Индекс региона | Изменение доступности на общей шкале | Одинаковая версия формулы и нормировки |
| Локальная доступность | Сколько возможностей достижимо из выбранных зон | Одни назначения, веса и функция затухания |
| Время по направлениям | Изменение важных поездок между территориями | Один набор OD-пар и весов |
| Задержки и перегрузка | Эффект на загруженных дорогах | Полное перераспределение потоков |
| Недоступный спрос | Поездки, для которых нет пути | Доля от неизменного исходного спроса |
| Устойчивость | Потеря доступности при закрытиях | Одинаковый набор сценариев отказа |
| Ресурсы | Стоимость, длина, полосы, сооружения | Разделение денежной оценки и физических ограничений |

Пример локальной доступности:

\[
A_i=\sum_j W_j\exp(-\lambda T_{ij}),\qquad
A_{local}=\frac{\sum_i P_iA_i}{\sum_i P_i}.
\]

Здесь веса возможностей \(W_j\), населения \(P_i\) и параметр затухания \(\lambda\) фиксированы. Для недостижимого назначения вклад равен нулю. Формула предлагается для локального показателя; она не подменяет действующую формулу регионального индекса без отдельной миграции.

Время доступных поездок показывается вместе с долей недоступного спроса. Улучшение среднего за счёт потери части маршрутов не считается победой.

Поиск возвращает набор Парето: варианты, которые нельзя улучшить по одной цели без ухудшения другой. Когда нужна одна рекомендация, пользовательская цель и ограничения задают порядок выбора. Произвольное сложение индекса, минут и рублей в один балл исключается из базовой версии.

## 6. Генератор проектов должен предлагать реализуемые изменения

| Тип проекта | Откуда берутся кандидаты | Ограничения |
| --- | --- | --- |
| Расширение | Устойчивые задержки, поток и дефицит мощности | Длина коридора, место, узлы на концах, число полос |
| Организация движения | Задержки на допустимых связях и узлах | Разрешённые режимы, скорость, ограничения поворотов |
| Новая связь | Большой объезд между близкими частями сети | Допустимый коридор, уклон, препятствия, длина |
| Резервирование | Значимая потеря доступности при отказе | Реальный альтернативный доступ и совместный расчёт |

У каждого кандидата есть геометрия, изменяемые рёбра, параметры, ресурсы, основания генерации и состояние проверки реализуемости. В качестве проектов рассматриваются связные коридоры с понятными концами, а не случайный набор раздельных линий.

Прямой отрезок между двумя узлами годится для поиска потенциального разрыва. Строительным предложением он становится после проверки коридора. Пересечение здания или водной преграды без предусмотренного сооружения отклоняется. Если необходимые геоданные отсутствуют, кандидат получает состояние `needs_feasibility_check` и не выдаётся как готовый проект.

Разрыв компонентов сначала проверяется как возможная ошибка исходной сети. Отсутствующее соединение в данных не является доказательством отсутствия дороги на местности.

## 7. Поиск сравнивает проекты и их сочетания

### 7.1. Базовый поиск работает без обученной модели

1. Проверить запрос, граф, зоны и исходный расчёт.
2. Построить общий допустимый пул проектов всех разрешённых типов.
3. Выполнить недорогой отбор по спросу, объездам, задержкам и критичности связей.
4. Рассчитать отдельные проекты в пределах бюджета, сохраняя разнообразие типов и территорий.
5. Построить пакеты жадным добавлением по пересчитанному предельному эффекту.
6. Улучшить пакеты операциями добавления, удаления и замены; сохранить несколько перспективных ветвей.
7. Уточнить лучшие результаты и вернуть подтверждённые варианты Парето.

Для небольшого пула полный перебор допустимых пакетов служит эталоном. Для большого предлагаются beam search и локальный поиск; ширина луча, размер пакета и бюджет определяются измерением, а не фиксируются как универсальные константы.

Пусть \(S\) — пакет, \(p\) — новый проект. Используется предельный эффект \(F(S\cup\{p\})-F(S)\). Сумма эффектов отдельных проектов не заменяет расчёт пакета: две дороги могут усиливать или обесценивать друг друга.

Не предполагается субмодулярность эффекта или гарантия качества жадного алгоритма. Для обнаружения взаимодополняющих проектов в поиске остаются парные изменения и несколько ветвей.

### 7.2. Лимит выдачи отделён от бюджета расчёта

`result_limit=3` означает три результата для пользователя. Он не означает проверку первых трёх кандидатов. Отдельно задаются `max_full_evaluations`, `wall_time_limit`, допустимые ресурсы и максимальный размер пакета.

Поддерживаются остановка, сохранение состояния и продолжение с совместимыми версиями входных данных. При исчерпании бюджета возвращается лучший проверенный вариант с объёмом выполненного поиска. Формулировка «оптимальный» допустима только при доказанной границе для исходной задачи.

### 7.3. Вся РФ требует иерархического поиска

На верхнем уровне оцениваются межтерриториальные коридоры, внешние потоки и доступность. Перспективные участки детализируются в локальных графах. Проверенный локальный проект обновляет параметры коридоров, после чего пересчитывается внешний эффект.

Запрос пары территорий сохраняет спрос и альтернативные пути между ними. Запрос региона рассматривает внутреннюю доступность и внешние связи. Общероссийский запрос распределяет бюджет поиска между территориями по явным правилам и ограничениям. Этот подход не даёт гарантии глобального оптимума по всем дорогам РФ.

## 8. Какие небольшие модели стоит рассмотреть

| Компонент | Роль | Решение для внедрения |
| --- | --- | --- |
| CatBoost | Оценка эффекта кандидата и неопределённости по табличным признакам | Первый обучаемый ускоритель после появления корректных примеров |
| TabPFN | Предобученная табличная регрессия для сравнительного эксперимента | Проверить при малом корпусе; зафиксировать checkpoint, лицензию и оборудование |
| Небольшая GNN | Оценка кандидата с учётом топологии, дорог и OD-связей | Следующий эксперимент при достаточном корпусе разных сетей |
| BoTorch | Выбор следующих дорогих вычислений с учётом неопределённости | Сравнить с базовым поиском на ограниченном пространстве решений |

### 8.1. CatBoost — первый практический кандидат

Начальные признаки: класс и длина дороги, полосы, мощность, свободная скорость, поток, задержки, число альтернатив, коэффициент объезда, проходящий OD-спрос, население в зоне влияния, параметры проекта и внешний транзит.

Модель оценивает отдельные эффекты: локальную доступность, задержки, недоступный спрос и при необходимости региональный индекс. Из прогнозов строится приоритет для следующего полного расчёта. Предложение, признанное недопустимым или не сошедшееся, не превращается в обучающий пример «эффект ноль».

CatBoost поддерживает оценки неопределённости и виртуальные ансамбли. Их калибровка на наших территориях проверяется отдельно: наличие API неопределённости не гарантирует её достоверность на новом регионе. [Документация CatBoost](https://catboost.ai/docs/en/references/uncertainty).

### 8.2. TabPFN — эксперимент для малого корпуса

TabPFN предоставляет предобученные модели для табличных задач, включая регрессию. Это позволяет проверить альтернативу обучению с нуля, но дорожные признаки, целевые значения и контроль качества всё равно нужны. Условия использования весов и требования к оборудованию проверяются для выбранной версии; работа на CPU с приемлемой задержкой не предполагается заранее. [Официальный репозиторий TabPFN](https://github.com/PriorLabs/TabPFN).

### 8.3. GNN полезна, когда табличные признаки теряют топологию

Предлагаемый эксперимент: компактная GIN/GINE либо гетерогенная сеть с дорожными и OD-связями. На входе локальный подграф вокруг проекта, внешние шлюзы, базовые потоки и описание изменения; на выходе прогноз эффекта или потоков.

Работа Madadi и Correia сочетает GNN, приближающую равновесие, с генетическим поиском инфраструктурных решений и предоставляет код. Её используем как образец эксперимента; перенос опубликованных результатов на наши данные требует проверки. [Статья](https://arxiv.org/abs/2303.06024), [код GIN–GA](https://github.com/bahmanmdd/HDLMF_GIN-GA).

Гетерогенная архитектура Liu и Meidani объединяет дорожную топологию и OD-связи, включая штраф за нарушение сохранения потока. Штраф в функции обучения не гарантирует точного выполнения физических ограничений. [Статья](https://arxiv.org/abs/2310.13193).

Начальную глубину и размер скрытого состояния выбираем по бенчмарку. Небольшой подграф без внешнего контекста может пропустить дальний объезд, поэтому радиус окрестности входит в проверку устойчивости.

### 8.4. BoTorch управляет очередью полных расчётов

Байесовская оптимизация выбирает следующие кандидаты по прогнозируемому улучшению и неопределённости. Для нескольких целей рассматривается подход через ожидаемое улучшение гиперобъёма Парето. Это инструмент поиска поверх оценщика, а не готовая модель дорожного строительства. [Описание BoTorch](https://github.com/meta-pytorch/botorch/blob/main/docs/overview.md), [многокритериальный поиск](https://botorch.org/docs/v0.16.1/tutorials/multi_objective_bo).

Применять его стоит к отобранному конечному пулу или компактному набору параметров. Представление миллионов дорожных рёбер независимыми бинарными переменными потребует другой декомпозиции и не считается решённым этим выбором библиотеки.

### 8.5. Обучаемый отбор сохраняет исследование новых вариантов

Каждая очередь вычислений содержит перспективные кандидаты, варианты с высокой неопределённостью и резерв для разнообразия или случайной проверки. Доли выбираются экспериментально. Низкий прогноз модели не становится постоянным запретом на проверку проекта.

После полного расчёта сохраняются новые признаки и метки. Итоговый ответ содержит только подтверждённые эффекты. Прогноз суррогатной модели остаётся внутренним инструментом планирования вычислений.

## 9. Контракты ядра отделяют поиск от чата

Ниже предложены интерфейсы, а не существующие модули репозитория.

| Контракт | Что хранит |
| --- | --- |
| `NetworkSnapshot` | Версию графа, геометрию, направления, мощности, ограничения |
| `DemandScenario` | Зоны, подключения, OD-матрицу, внешние потоки, период, seed |
| `ProjectCandidate` | Тип, геометрию, изменения рёбер, ресурсы, состояние допустимости |
| `Portfolio` | Набор совместимых проектов и совокупные ограничения |
| `EvaluationResult` | Метрики до/после, сходимость, недоступный спрос, проверенный статус |
| `SurrogatePrediction` | Прогнозы, неопределённость, версию модели и признаки |
| `SearchBudget` | Лимиты времени, полных расчётов, размера пакета и выдачи |
| `SearchResult` | Проверенные варианты, объём поиска, причину остановки, ссылки на расчёты |

Состояния оценки: `invalid_input`, `needs_feasibility_check`, `nonconverged`, `evaluated`, `verified`. Причины не сворачиваются в числовой эффект. Отсутствие полезных вариантов является допустимым результатом.

Чат передаёт структурированный запрос и объясняет готовые результаты. Карта получает геометрию из того же `ProjectCandidate`: изменяемые существующие участки выделяются красным, предлагаемые новые участки — ярко-зелёным. Служебные подключения зон и точки на зданиях не становятся объектами рекомендации.

Ключ кэша включает версии сети, спроса, подключений, решателя, параметров метрик и каноническое описание пакета. Изменение исходных данных инвалидирует несовместимые результаты и прогнозы.

## 10. Как проверять математику и качество поиска

### 10.1. Контрпримеры обязательны до обучения

| Сценарий | Ожидаемое свойство |
| --- | --- |
| Жилой тупик у одной из точек города | Закрытие не изолирует весь город через ошибку представления |
| Единственный настоящий мост | Потеря доступа сохраняется; перепривязка её не скрывает |
| Две параллельные дороги | Поток перераспределяется с учётом направлений и ограничений |
| Разрыв графа | Недоступный спрос учитывается и не улучшает среднее удалением поездок |
| Запрещённый поворот | Объезд соблюдает запрет |
| Новый коридор через здание | Строительное предложение отклоняется |
| Два взаимодополняющих проекта | Поиск пакетов обнаруживает совместный эффект |
| Сеть Браесса | Добавление связи может ухудшить равновесное время; эффект не принуждается к плюсу |
| Проект у края территории | Расширение области не меняет вывод сверх заданного допуска |
| Нет полезных проектов | Возвращается отсутствие подтверждённого улучшения |

Для графа с фиксированными неотрицательными временами удаление ребра не сокращает кратчайший путь, а уменьшение веса не увеличивает его. Эти проверки применяются к маршрутизатору. При равновесном перераспределении потоков такие утверждения нельзя автоматически переносить на итоговые времена всех поездок.

### 10.2. Сравнение решателей и поиска разделяется

Решатель проверяется на стандартных сетях транспортного распределения и российских подграфах: баланс потоков, сходимость, согласованность с эталоном, время и память. Исторические проверки AequilibraE на Sioux Falls, Anaheim и других сетях показывают подход к валидации, но не дают наших показателей скорости. [Traffic Assignment Validation](https://aequilibrae.com/docs/python/V.1.1.4/traffic_assignment/traffic_assignment_validation.html).

Поиск сравнивается с полным перебором на малых задачах и с одинаково ограниченными случайным отбором, жадным и локальным поиском на больших. Бюджеты считаются и по числу полных расчётов, и по полному времени, включая прогнозы, подготовку признаков и обучение, если оно входит в сценарий запуска.

Основной критерий: качество лучшего подтверждённого решения при одинаковом бюджете. Дополнительно измеряются потеря относительно известного лучшего решения, охват полезных кандидатов, качество фронта Парето и доля неподтвердившихся прогнозов. Малой ошибки регрессии недостаточно, если модель пропускает лучшие проекты.

### 10.3. Обучение проверяется на других территориях

Обучающая выборка собирается только из расчётов, прошедших проверки графа, подключений и сходимости. Разделение проводится по городам и регионам; соседние участки, варианты одного проекта и связанные сценарии не должны попадать одновременно в обучение и проверку.

Отдельно проверяются новые уровни спроса, классы дорог, внешние потоки и редкие разрывы сети. Для неизвестного режима система увеличивает долю полного поиска. Наблюдаемая точность в одном городе не объявляется переносимостью по РФ.

## 11. В каком порядке внедрять

| Этап | Результат | Условие завершения |
| --- | --- | --- |
| 1. Граф и зоны | Направления, распределённый доступ, неизменные подключения | Пройдены контрпримеры тупика, моста и поворота |
| 2. Численный оценщик | Равновесие, недоступный спрос, локальные метрики и индекс | Сходимость и точность сравнений подтверждены эталонами |
| 3. Генератор и поиск | Допустимые коридоры, общий пул, пакеты и ограничения | На малых задачах результат сопоставлен с полным перебором |
| 4. CatBoost | Прогноз и неопределённость для очереди вычислений | Превосходит базовый поиск при одинаковом бюджете на других городах |
| 5. GNN / TabPFN / BoTorch | Сравнительные эксперименты | Дополнительная сложность даёт подтверждённое улучшение поиска |
| 6. Иерархия РФ | Отбор коридоров и локальная детализация | Проверена устойчивость границ и согласованность внешних потоков |

До экспериментов фиксируются сети, сценарии, бюджеты, допуски и правило успеха. Конкретные пороги времени и качества выбираются под стенд и объём данных; неподтверждённые значения в требования не подставляются.

Первый законченный результат — корректный оценщик и детерминированный поиск без обучаемой зависимости. Он одновременно даёт рабочие рекомендации, эталон сравнения и корпус для небольших моделей. Каждая последующая модель принимается по качеству проверенных решений при заданном вычислительном бюджете.


## Решения реализации, 12 ноября 2026

Принятые условия: связанность является основной целью, перегрузка показывается явно; денежного бюджета нет. Допускаются полноценные трассы, мосты, тоннели и выход за выбранные регионы. Поиск ограничен минутой, без фонового продолжения, до 32 процессов. Время LLM вне лимита. Основной путь один: генерация по географии, обязательный CatBoost, подтверждение через локальные diff. Полные расчёты используются как эталон обучения и проверки. Реализация и текущие ограничения: [методика](network-development.md).
